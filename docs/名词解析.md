# FDP / FDK 名词解析（白话版）

> 版本：v1.0  
> 日期：2026-07-22  
> 用途：读使用指南、context、口令时对照；**不要求一次记完**  
> 分类维度：按「你在干什么」分组（流程 → 关卡 → 文档 → 检查 → 增强口令 → 易混词）

遇到不懂的词，先在本页搜中文或英文缩写。

---

## 一、最大的几个词（先看这 5 个）

| 词 | 一句话 |
|----|--------|
| **FDK** | Feature Delivery Kit：这套「交付工具包」仓库本身（Skills、模板、Hook） |
| **FDP** | Feature Delivery Pipeline：用这套工具跑的一条「功能交付流水线」 |
| **feature** | 正在做的那个功能名（如 `work-brief` = 工作汇报） |
| **Converge** | 开发后对照清单**查漏**，直到该做的都做完（也叫「收敛」） |
| **门禁** | 关卡：没过就不能随便进下一步（例如没确认清单就不能写业务代码） |

关系可以记成：

```text
FDK = 工具箱
FDP = 用工具箱走的那条产线
feature = 这次产线上的产品（某个功能）
```

## 二、流程相关

| 词 | 白话 | 你什么时候会碰到 |
|----|------|------------------|
| **流水线 / 步骤 1～6** | 从需求到交付的固定顺序 | 说「按 FDP 全流程」 |
| **entry_mode** | 「从哪一站开始」：全流程 / 从方案 / 从清单 / 从开发… | 「检测产物从哪开始」 |
| **from_spec_lock** | 方案有了，还没确认清单 → 从「生成清单」开始 | 常用入口 |
| **from_development** | 清单已确认 → 可以写代码 | checklist 已 approved |
| **fast_track / 快速通道** | 小改动，走简化流程（仍建议有轻量验收） | 「加个字段」「简单改动」 |
| **activeFeature** | 配置里写「当前正在做哪个功能」；空 = 不拦日常写代码 | `.cursor/fdp.config.json` |
| **复杂度 simple / standard / complex** | 简单 / 标准 / 复杂；决定门禁严不严、要不要完整 Analyze | context / checklist 头上 |

## 三、门禁（关卡）编号

| 编号 | 名称 | 白话：过关意味着 |
|------|------|------------------|
| **G1** | 需求确认 | 需求大致对齐了，可以写产品说明 |
| **G2** | 方案确认 | 技术方案你点头了 |
| **G3** | Spec Lock / 清单锁定 | **你确认过验收清单**，允许开发（最重要的人工关） |
| **G4** | Analyze | 开发前文档互相不矛盾、没有阻断级问题 |
| **G5** | 开发门禁 | Hook：标准/复杂功能未过 G3 时，拦着不让乱写业务代码 |
| **G7** | Converge | 查漏通过：清单上的 P0 都落地了 |
| **G8** | 交付确认 | 文档/接口等收尾完成 |

状态常见写法：`⏳` 未过、`✅` 已过。

## 四、规格与清单（Spec 一族）

| 词 | 白话 |
|----|------|
| **Spec Lock** | 开发前把「要做什么」写成可检查的合同，并让你确认 |
| **AC / 验收项** | Acceptance Criteria：一条条「做完应该怎样」；编号如 `AC-RND-01` |
| **P0 / P1** | 优先级：P0 必须做完才能宣称收敛；P1 可延后（如纯视觉） |
| **RTM** | 追溯表：哪条 AC ↔ 哪段实现 ↔ 哪个测试 |
| **ui-spec** | 页面结构规格：有哪些筛选、列、分栏（偏「长什么样的结构」） |
| **acceptance-checklist** | 汇总清单；头上的 `approved: true` = 你已批准可开发（G3） |
| **approved: true** | 清单文件最上方 YAML 里：人确认过了 |
| **Analyze** | 写代码前审文档：有没有互相打架、漏写结构项 |
| **spec-analyzer / spec-verifier** | 只读审查用的独立 Agent（避免「自己写自己审」） |

## 五、context.md 里常见节

`context.md` = 这个功能的**进度板 + 决策本**（给人和 AI 读）。

| 节 / 词 | 白话 |
|---------|------|
| **流水线状态** | 当前功能名、从哪开始、走到第几步 |
| **门禁状态** | 各关卡过了没 |
| **SSOT** | Single Source of Truth：**以哪份文档为准**（产品说明、原型、技术方案…） |
| **领域词表** | 本功能统一说法，减少人和 AI 各说各话（例：Round = 汇总周期） |
| **评审确认项（D1、D2…）** | 讨论定下来的结论，避免以后再翻案 |
| **待澄清（Q1…）** | 还没问清的问题；标 P0 的会卡住开发 |
| **执行进度** | 产品 / 开发 / 查漏各阶段完成情况 |
| **MECE 自检** | 写文档时自检：分类有没有重叠、有没有漏场景（见下文「MECE」） |

## 六、检查与「双轴」

| 词 | 白话 |
|----|------|
| **Converge / 收敛** | 开发后对照清单查漏；有漏就补，再查，直到 P0 清零 |
| **converge-report** | 查漏报告（第几轮、还剩哪些 AC） |
| **round（Converge 的轮次）** | 第几次查漏循环，不是业务里的「汇总周期 Round」——**两个 Round 别混** |
| **双轴审查** | 检查分两拨，分开写结论 |
| **规格轴** | 「需求 / 清单做对了没？」→ 主要靠 Converge |
| **规范轴** | 「代码写得合不合项目规范？」→ 主要靠代码审查 / cross-review |
| **为什么要分两轴** | 防止「代码还行」被当成「功能做齐了」 |

## 七、UI 相关

| 词 | 白话 |
|----|------|
| **结构复核（P0）** | 对照原型：筛选项、表格列、左右栏、展示格式有没有漏/多 |
| **视觉（P1）** | 间距、颜色、字体等观感；不挡「功能收敛」，但提测前建议看 |
| **ui-diff-checklist** | UI 走查勾选表 |
| **原型保真 / TRAP-UID / U1～U6** | 防「做成了但和原型结构不一致」的检查项编号（细节见专用规则文档） |

## 八、增强口令（1.6 起）

| 词 / 口令 | 白话 |
|-----------|------|
| **grill / 对齐一下** | 开发前把模糊点一个个问清，并更新词表、确认项 |
| **diagnose / 诊断** | 硬 bug：先复现、再缩小范围、再假设、再改，最后补测试 |
| **handoff / 交接** | 换聊天窗口继续做：写一份「做到哪、下一步说什么」 |
| **踩坑回流 / 晋升 FDK** | 把这次踩的通用坑沉淀进工具包（要可复用才改 FDK） |

## 九、容易混淆的词

| 容易混 | 怎么区分 |
|--------|----------|
| **FDK vs FDP** | FDK=工具包；FDP=跑起来的流水线 |
| **Round（业务）vs round（查漏）** | 业务 Round=汇总周期；查漏 round=第几次 Converge |
| **规格轴 vs 规范轴** | 规格=需求对不对；规范=代码好不好 |
| **Analyze vs Converge** | Analyze=写代码**前**审文档；Converge=写代码**后**查漏 |
| **正交** | 两件事各管各的、互不顶替（例：查漏 ≠ 架构体检） |
| **Hook** | Cursor 里自动触发的脚本（如未批准清单就拦写代码） |
| **Skill** | 给 AI 看的操作说明书（`.cursor/skills/.../SKILL.md`） |
| **canonical** | FDK 的「唯一维护源」仓库；业务项目通过联接/安装同步 |

## 十、其它缩写速查

| 缩写 | 全称 / 含义 |
|------|-------------|
| **PRD** | 产品需求说明 |
| **AC** | 验收标准（Acceptance Criteria） |
| **RTM** | 需求追溯矩阵 |
| **ADR** | 架构决策记录（重要技术决定为什么这么选） |
| **TRAP-*** | 踩坑模式编号（如批量循环里发号等） |
| **SSOT** | 唯一可信来源 |
| **MECE** | 分类「不重叠、不遗漏」的自检原则 |

## 十一、一条线串起来（记住顺序即可）

```text
对齐（问清）→ 产品/方案 → 清单确认(G3)
    → 开发前审文档(Analyze)
    → 写代码 + 测试
    → 查漏(Converge / 规格轴) + 代码审查(规范轴)
    → 交付
```

日常对 AI 可以说人话，例如：

- 「对照清单查漏」≈ 执行 Converge  
- 「先把需求问清楚」≈ grill  
- 「清单我确认了可以开发」≈ 把 checklist 的 `approved` 设为 true

## MECE 自检

- 分类维度：流程 × 门禁 × 规格 × context × 检查 × UI × 增强口令 × 易混词  
- 无重叠：同一词只在一处给主定义，易混节做对照  
- 无遗漏：日常口令与 context 常见节已覆盖；⚠️ 具体 TRAP 场景码见 `prototype-fidelity-rules` / `common-traps`，本文件不展开
